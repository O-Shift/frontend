## 1. Surrogate vs natural keys

A **natural key** is a real-world attribute that happens to be unique — an email address, an SSN, a SKU. A **surrogate key** is a value the database invents purely to identify a row — an auto-incrementing integer, a UUID.

Default to surrogate keys as primary keys, and keep natural/business identifiers as unique constraints instead of primary keys. The reasoning: natural keys have a well-documented habit of turning out less unique or less permanent than they seemed at design time.

- Emails get reassigned or reused after an account is deleted.
- SSNs get reused across different national contexts, or a business decides it shouldn't have been storing them as a key at all.
- SKUs and product codes get renumbered when a company reorganizes its catalog.
- "Surely this is unique" almost always eventually meets an exception nobody anticipated (a merger, a duplicate entry that has to be fixed retroactively, an international customer whose "unique" identifier scheme doesn't apply to them).

When a natural key changes, every foreign key referencing it as a primary key has to cascade-update, which is exactly the kind of expensive, risky, all-at-once operation you want to avoid needing. A surrogate key never has to change for business reasons, because it was never a business fact in the first place — so keep the natural key as a `UNIQUE` constraint (you still get the "no duplicate emails" guarantee) without making it load-bearing for every relationship in your schema.

## 2. Choosing the surrogate key type

The real options, compared on the dimensions that matter in practice:

| | Auto-increment integer/bigint | UUIDv4 (random) | UUIDv7 (time-ordered) / ULID |
|---|---|---|---|
| Size | 4 or 8 bytes | 16 bytes | 16 bytes (UUIDv7) / 16 bytes (ULID) |
| Index locality | Excellent — always inserts at the end of the B-tree | Poor — random values insert all over the index, causing page splits and bloating cache footprint | Good — time-ordered, so it inserts at the end like an integer |
| Sortable by creation time | Yes, incidentally | No | Yes, by design |
| Generatable without coordination (multiple services/offline clients) | No — needs the database to hand out the next value | Yes | Yes |
| Leaks information if exposed publicly | Yes — sequential IDs reveal row counts/volume and are trivially enumerable (`/orders/1042` implies `/orders/1041` exists) | No | Only the rough creation time, not volume or ordering position |
| Human-readable in logs/debugging | Easy | Painful | Somewhat easier (sortable, and ULID has a compact text form) |

**Why UUIDv4 has a real, measurable downside, not just a theoretical one:** because its bits are fully random, consecutively-inserted rows land at random positions in a B-tree index rather than appending at the end. That causes index page splits and worse cache locality, which shows up as real, measurable insert throughput loss on large, write-heavy tables — this is the actual mechanism behind "UUIDs are slow as primary keys," not vibes.

**UUIDv7 fixes this** by putting a millisecond-precision timestamp in the most significant bits, so newly generated UUIDs sort — and therefore insert — in roughly chronological, append-mostly order, while keeping the rest of the value random for global uniqueness. It's a real IETF standard (RFC 9562, published May 2024), not a proprietary scheme, and current PostgreSQL (18+) has it built in: `uuidv7()` to generate one, and `uuid_extract_timestamp()` to pull the embedded timestamp back out. On older Postgres versions, or other databases, an equivalent value can be generated in application code or via a small SQL function — there are widely-used, well-tested implementations to borrow rather than inventing your own. ULIDs solve the same problem with a slightly different encoding (commonly rendered as a compact 26-character string) and are a reasonable equivalent choice, especially in ecosystems where ULID tooling is already the convention.

## 3. Decision framework

- **Single database, no need to hide sequence/volume information, want the smallest index and the simplest mental model** → `bigint` identity/auto-increment. Still perfectly reasonable for plenty of applications, especially internal tools or anything where IDs are never exposed to end users.
- **IDs need to be generated by multiple services or offline clients without a round-trip to ask the database "what's next"** (microservices, mobile apps that create records offline, distributed writers) → UUID. Coordination-free generation is the whole point.
- **You're using UUIDs *and* care about insert performance on a large or write-heavy table** → UUIDv7 (or ULID) over UUIDv4, essentially without exception. There is very little reason to choose random UUIDv4 for a primary key once UUIDv7 is available to you — it gives you the coordination-free generation of a UUID with much better index behavior.
- **IDs will ever be exposed in a URL or an API response** → don't assume this decides your PK type. You can always keep an efficient internal PK (integer or UUIDv7) and add a separate opaque public-facing identifier (a random slug or short ID) for anything you don't want to be guessable or enumerable — see §6. Conflating "efficient internal key" with "safe public identifier" is a common and avoidable mistake.

## 4. Composite keys

A composite key (multiple columns together forming the key) is most defensible on pure junction/join tables — e.g., a `team_members` table might reasonably use `(team_id, user_id)` as its primary key, since that pair is genuinely what uniquely identifies a membership row and there's rarely a reason for anything else to reference a specific membership by its own ID.

The trade-off: the moment something *does* need to reference that row directly — a comment on a specific membership, an audit entry, anything — a 2- or 3-column composite foreign key has to propagate through every table that references it, which gets unwieldy fast. Default to a single surrogate key plus a `UNIQUE (team_id, user_id)` constraint (which still fully enforces "no duplicate membership") unless you're confident nothing will ever need to reference the row individually.

## 5. Foreign key design and cascade behavior

Always index foreign key columns explicitly — most databases index primary keys automatically but do not do the same for foreign keys, and an unindexed FK is one of the most common, and most avoidable, causes of a slow join or slow cascading delete that nobody can immediately explain.

`ON DELETE` behavior is a real design decision per relationship, not a default to leave unconsidered:

- **`CASCADE`** — deleting the parent deletes children automatically. Convenient, and appropriate when children genuinely have no independent existence (deleting a `project` should delete its `project_settings` row). Dangerous when applied broadly to anything a user might delete casually but regret losing everything downstream of — think hard before cascading deletes across several hops of an ownership chain.
- **`RESTRICT` / `NO ACTION`** — deleting the parent fails if children exist. Safer default for high-stakes or ambiguous cases: it forces an explicit decision (delete the children first, or reassign them) rather than silently taking one for you.
- **`SET NULL`** — the child survives, its FK becomes null. Appropriate when the relationship is genuinely optional and the child's existence shouldn't depend on the parent's (e.g., an order's `referred_by_user_id` — if that user is deleted, the order should still exist).
- **`SET DEFAULT`** — rarely useful outside specific lookup-table scenarios; mention it exists, don't reach for it by default.

## 6. Decoupling display identifiers from primary keys

Order numbers, invoice numbers, ticket numbers — anything a human types, reads aloud, or expects to look "clean and sequential" — should be a separate column, not the primary key, even if it looks unique enough to serve as one.

The genuinely tricky, commonly-needed case is **per-tenant sequential numbering** — e.g., every company's invoices should start at #1 and increment gaplessly, independent of every other tenant's invoice numbers. A single global sequence doesn't give you this. Real options, in order of how much correctness they buy you:

1. **A counters table**, one row per tenant per sequence type, incremented inside the same transaction as the insert using `SELECT ... FOR UPDATE` (or `UPDATE ... RETURNING` as an atomic increment-and-read). Guarantees gapless, per-tenant sequential numbers, at the cost of that row becoming a serialization point for concurrent inserts within one tenant — usually a perfectly acceptable trade-off, since invoice creation for a single tenant is rarely high-frequency enough for this to matter.
2. **A Postgres sequence per tenant.** Works, but means creating a new sequence object every time a tenant is created — reasonable if the tenant count is bounded and tenant creation is already a deliberate provisioning step; awkward at very large tenant counts.
3. **Accept gaps.** If "gapless" isn't actually a hard requirement (many businesses only assume it is until asked directly), a per-tenant counter that can occasionally skip a number under concurrent load is much simpler to implement safely. Worth explicitly confirming with the user whether gaplessness is a real requirement (sometimes a legal/accounting one) or an assumption — it changes which of these options is worth the complexity.

Whichever approach you choose, keep the internal primary key (integer or UUID) as what every other table's foreign keys actually reference — the display number is presentation, not structure.
