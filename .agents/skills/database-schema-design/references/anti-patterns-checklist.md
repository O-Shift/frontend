# Anti-patterns checklist

Run the finished design against this list deliberately before calling it done — don't just assume you avoided these. If you knowingly broke one with a real reason (some, like denormalization, are sometimes the right call), say so explicitly in the design doc. If you find one you didn't intend, fix it now — it's far cheaper before the schema ships than after.

| # | Anti-pattern | Why it hurts | The fix |
|---|---|---|---|
| 1 | **EAV / generic "attribute-value" tables** used to dodge a modeling decision | Loses real types, constraints, and indexes; simple filters become self-joins per attribute | Real columns where you can; a scoped JSONB column for genuine flexibility; a proper metadata-driven custom-fields system only when end users truly need runtime-defined fields — see `data-modeling-and-normalization.md` §7 |
| 2 | **Comma-separated values in one column** (`tags = "red,blue,green"`) | Can't index, filter, or join on individual values without string-parsing hacks | A join table, or an array/JSONB column with a proper GIN index |
| 3 | **Floats for money** | Binary floating point can't represent most decimal fractions exactly; errors compound into real accounting discrepancies | Integer minor units (cents) or fixed-point `DECIMAL`/`NUMERIC` |
| 4 | **"God table"** — one huge table covering many unrelated concerns because splitting it felt like more work | Every unrelated concern's schema changes touch the same table; nullable columns pile up because most rows don't need most fields | Split by actual entity and actual lifecycle, per `data-modeling-and-normalization.md` |
| 5 | **Generic `type` + `value` catch-all columns** instead of real columns or tables | A narrower variant of #1 — same loss of types, constraints, and queryability | Real columns, or a real polymorphic pattern from `relationships-and-hierarchies.md` §4 if the "type" is actually about which parent entity something belongs to |
| 6 | **No foreign key constraints at all**, "for performance" or "for flexibility" | Referential integrity becomes an application-code-only promise, which a bug, a bypassed code path, or a bulk import will eventually break silently | Add real FK constraints; the performance concern is usually overstated relative to the correctness benefit, and if it's a genuine, measured bottleneck at extreme scale, that's a narrow, specific optimization — not a default posture |
| 7 | **Missing indexes on foreign key columns** | One of the most common causes of an unexplainably slow join or slow cascading delete | Index every FK explicitly — see `indexing-and-performance.md` §5 |
| 8 | **A natural key used as primary key that turns out not to be stable** (email, SSN, phone number) | The moment it needs to change, every FK referencing it has to cascade-update — an expensive, risky, all-at-once operation | Surrogate key as PK; natural key as a `UNIQUE` constraint instead — see `keys-and-identifiers.md` §1 |
| 9 | **Sequential, guessable public-facing IDs** (`/invoices/1042`) | Reveals row volume; enables enumeration of other tenants'/users' records if authorization is ever even briefly misconfigured | UUID (ideally UUIDv7) as the PK, or a separate opaque public identifier even with a sequential internal PK — see `keys-and-identifiers.md` §2, §6 |
| 10 | **Timezone-naive timestamps** | Off-by-one-hour bugs the moment a user is in a different timezone or DST shifts | `timestamptz`, always stored in UTC, converted only for display |
| 11 | **Polymorphic `type` + generic `id` columns with no DB-enforced integrity** | The database can't verify the referenced row actually exists in the right table; drifts silently on any bug or bypass | Prefer exclusive-arm nullable FKs when the parent-type set is small and stable — see `relationships-and-hierarchies.md` §4 |
| 12 | **No consistent soft-vs-hard-delete decision** — some tables have `deleted_at`, some don't, with no stated reason for the difference | Inconsistent, surprising behavior; some "deleted" data reappears somewhere it wasn't expected to, some is gone when someone hoped for undo | Decide per entity, deliberately, and state the reason — see `common-patterns-and-conventions.md` §3 |
| 13 | **Over-normalized past the point of practicality** — technically correct 3NF+ everywhere, but a single page load needs ten-plus joins | The opposite failure from EAV: theoretically pure, practically painful; every read pays a join tax nothing actually needed | Denormalize deliberately and locally for the specific, measured hot paths — see `data-modeling-and-normalization.md` §4, or use a materialized view (§5) |
| 14 | **Unbounded, unpartitioned append-only tables** (logs, events, audit trails) with no retention or partitioning plan | Backups, indexes, and routine maintenance (vacuum, etc.) get slower indefinitely as the table grows forever | Partition by time and drop old partitions, or define and enforce a real retention policy — see `indexing-and-performance.md` §7 |
| 15 | **Multi-tenancy retrofitted inconsistently** — some tables have `tenant_id`, some don't; RLS applied to some tables but not others | The exact shape of a real cross-tenant data leak — inconsistency here isn't a style issue, it's a security gap | Every tenant-scoped table gets `tenant_id` and an RLS policy, applied uniformly — see `multi-tenancy-patterns.md` §3 |
| 16 | **Invariants enforced only in application code**, never backed by an actual DB constraint | Works until a background job, a migration script, an admin console, or a plain bug bypasses the application layer that was the only thing enforcing it | Push what you can into `CHECK` constraints, `NOT NULL`, foreign keys, and unique constraints — see the golden rules in SKILL.md |
